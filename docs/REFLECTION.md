## 1. 새로고침해도 남아야 할 데이터는? 백엔드와 DB는 각각 무엇을 하나요?
- 남아야 할 데이터: 할 일(제목, 완료 여부, 마감일, 카테고리), 카테고리, 사용자 계정.
- 화면에만 있는 데이터는 새로고침하면 사라집니다. 그래서 DB에 저장해야 합니다.
- **백엔드**: 요청을 받아 입력을 검사하고, 로그인한 사용자인지 확인한 뒤 DB를 호출해 결과를 응답합니다. (`server/routes/*.js`)
- **DB**: 데이터를 저장하고 조건으로 찾아 주며, 제약(필수값, 길이, 중복 불가, 외래키)과 접근 규칙(RLS)으로 데이터를 지킵니다.

## 2. 데이터베이스가 발전한 이유 하나 (파일 → 관계형)
파일에 적으면 같은 정보가 여러 곳에 중복되고 서로 어긋나기 쉽습니다. 관계형 DB는 정보를 표로 나누고 외래키로 연결해 일관성을 지킵니다.
내 앱에서는 카테고리 이름을 `categories` 표 한 곳에만 두고 할 일은 `category_id`로 가리켜서, 이름을 바꿔도 모든 할 일에 반영되고 카테고리를 지워도 할 일이 사라지지 않게 했습니다.

## 3. 내 Todo 앱의 표·항목·관계, 그리고 SELECT
- `categories`(id, user_id, name, color, created_at)
- `todos`(id, user_id, title, is_done, due_date, category_id, created_at, completed_at)
- 관계: 카테고리 1 : 할 일 N. `todos.category_id` → `categories.id`.

"오늘 마감인 미완료 할 일을 카테고리 이름과 함께":
```sql
SELECT t.title, t.due_date, c.name AS category
FROM todos t
LEFT JOIN categories c ON c.id = t.category_id
WHERE t.is_done = false AND t.due_date = current_date
ORDER BY t.due_date;
```
- `SELECT` 무엇을 보여 줄지, `FROM` 어느 표에서, `WHERE` 어떤 조건의 행만.
- `LEFT JOIN`을 쓴 이유: 카테고리가 없는("미분류") 할 일도 목록에 나와야 하기 때문입니다.

## 4. 로그인한 사용자가 자기 할 일만 보게 하려면?
1. 로그인은 직접 만들지 않고 검증된 Supabase Auth를 씁니다.
2. 로그인하면 토큰을 받고, 백엔드가 이 토큰으로 DB를 호출합니다. (토큰은 `httpOnly` 쿠키라 화면의 JS가 못 읽음)
3. 할 일의 `user_id`는 요청에서 받지 않고 **DB가 `auth.uid()`로 채웁니다.** 화면이 보낸 값은 믿지 않습니다.
4. RLS 정책이 `user_id = auth.uid()`인 행만 조회·추가·수정·삭제하게 합니다.
5. 백엔드에 `service_role` 키를 두지 않습니다. 그 키는 RLS를 우회하기 때문입니다.
- 확인: 두 계정으로 `scripts/verify-rls.js`를 실행해 13개 항목이 모두 통과했습니다. B가 A의 할 일을 조회하면 0건이고, 수정·삭제는 0건이며, A의 `user_id`로 속여 추가하면 거절됩니다.

## 5. SQL 주입과 비밀번호 유출을 막고 데이터를 복구하려면 AI에게 무엇을 요구할까?
- **SQL 주입:** "SQL 문자열에 사용자 입력을 이어 붙이지 말고, 라이브러리의 파라미터 바인딩/쿼리 빌더만 써 줘. 입력은 서버에서 검증해 줘." → 이 앱은 `supabase-js`의 쿼리 빌더만 사용하고, 제목 길이·날짜 형식·id 정수 여부를 서버에서 검사합니다.
- **비밀번호:** "비밀번호를 직접 저장하거나 로그에 남기지 말고, 해시를 다루는 검증된 인증 서비스를 써 줘." → Supabase Auth가 처리하고 우리 DB 표에는 비밀번호 열이 없습니다.
- **키:** "접속 키는 `.env`에만 두고, 화면 코드에는 쓰지 말고, secret 키는 쓰지 마." → 서버가 secret 키를 감지하면 시작을 거부하게 했습니다.
- **복구:** "스키마를 SQL 파일로 남기고, 백업 정책을 알려 주고, 복구를 실제로 해 보는 절차를 줘."
  - 한 것: 표와 RLS 정책을 `supabase/schema.sql`로 저장소에 보관해 같은 구조를 다시 만들 수 있고, 로컬 버전은 Git 태그로 남겼습니다.
  - [ ] 아직 안 한 것: 데이터 백업을 내려받고 복구해 보는 연습.
